## 2026-07-08 — 방향 확정: JKICS 투고 + 대역폭 저감 프레이밍

### 큰 결정
- **투고처 = JKICS(한국통신학회논문지, 국문 KCI)**. → 탑 로보틱스 학회 기준의 비관은 해당 없음. 심사자는 통신·IT 연구자.
- **프레이밍 전환: "연산량 감소" → "데이터/대역폭 저감(task-oriented communication)".**
  이유: SUPER는 raycasting-free라 점을 잘라도 CPU가 안 줄어듦(구조적). 반면 **점 66% 저감 = 대역폭/전송량 저감**은 실측 사실이고 통신 저널에 정합.

### 실측으로 확정된 사실 (이번 arc 전체)
- **점 66%↓** (프레임당 64k→22k). 기하학적으로 정확. ← 논문 헤드라인 숫자.
- **CPU**: raycasting-free SUPER는 무변(112%≈116%). raycasting/OGM 켤 때만 ~15%↓(156→138). → "연산량 대폭↓" 주장 금지.
- **속도**: FoV 축소로 안 바뀜(SUPER replan은 점 수 무관, traj-opt+backup 지배). "속도 스토리" 폐기.
- **안전(정적)**: sector는 안전 무손실(SUPER safety-assured가 sensing-cut을 보수화로 흡수). "sector 안전↓→adaptive 복구" 스토리 정적에선 폐기.

### adaptive의 정직한 위치
- **주인공 불가**: CPU 못 줄임, 정적 안전 결손 없음(복구할 것 없음), 동적 blind-zone mover 못 구함.
- **정당한 역할 = task-oriented 저감의 메커니즘**: 항법 태스크에 필요한 방향=진행방향이고 그게 시시각각 변하므로, **고정 sector가 아니라 velocity-정렬 adaptive**가 "태스크 관련 FoV만 유지"를 제대로 달성. 단 이점은 **heading≠velocity**일 때만.

### FoV-awareness 구현 (내가 짠 코드 — 논문 방법론 중심)
- SUPER `FOVChecker`는 OMNI 하드코딩(수직 cut만). 여기에 **수평 ±각 cut 추가**(`fov_horizontal_angle`, `fov_center_heading`; `getFovCheckPlane`에 좌우 평면 2개, `cutPolyByFov` 중심 선택). config `use_fov_cut:true`.
- 효과: 미감지=unknown 처리 → sensing-cut의 대가를 **크래시 → 보수적 정지**로 전환.
- 정량화: dense forest에서 **±60°는 과보수(13m 기어감), ±90°는 완주(86m).** full(360°)은 88m 완주. → 안전-보수화 trade-off 노브.

### 적용 경계 지도 (형이 반례로 직접 규명)
| 시나리오 | 수평 sector 저감 | 이유 |
|----------|------------------|------|
| 정적 전방항법 | ✅ 대역폭 free lunch | 안전·완주 무손실(정적), yaw가 콘을 경로에 맞춤 |
| 동적 장애물 | ❌ 위험 | 꺼진 방향 mover 못 피함, adaptive도 못 구함 |
| 고정기수/벽면검사 | ❌ 커버리지 상실 | 다방향(벽+경로+수직) 필요, 단일 콘으로 못 자름 |
| raycasting-free 플래너 | CPU 무변 | 점 수 무관 |
| occupancy/ESDF 플래너 | CPU↓ | 매핑이 점/광선 비례 |

### 왜 대역폭을 줄여야 하는가 (motivation, JKICS 서론용)
1. LiDAR 데이터량 큼: Mid-360 ~20만점/s ≈ 25–30 Mbps; 고밀도 센서 수백 Mbps.
2. UAV는 무선 전송/오프로딩 多: GCS 전송, 엣지/클라우드 오프로딩(SWaP 제약), 스웜 공유채널.
3. 무선 링크 제한·가변(WiFi/LTE/전용링크, 거리·간섭·스펙트럼 공유) → 초과 시 지연·손실·프레임드롭 → 실시간 제어 위험.
4. 전송 에너지 = 데이터량 비례 → 배터리 제약.
5. → **태스크 인지 저감**(항법에 필요한 FoV만 유지)으로 66%↓, 태스크 무손실. = task-oriented/semantic communication 흐름.
- 정직 단서: LiDAR는 물리적으로 360° 계속 생성 → 필터는 **전송/처리 데이터량**을 줄이는 것(센서 생성량 아님). 동기는 **전송/오프로딩/스웜** 시나리오에 겨눔.

### 논문 구조 (JKICS 국문 초안)
서론(대역폭 동기) / 관련연구(LiDAR 플래너, 데이터 저감, task-oriented comm) / 제안기법(sector 필터+velocity-정렬 adaptive+FoV-aware+SUPER 통합) / 실험(데이터 66%↓·안전·완주·±60/±90 trade-off) / 논의·한계(동적·검사·CPU 경계) / 결론.

2. **매핑 비용도 실제로 감소**: raycast 65%↓, ROG 총 매핑시간 56%↓ (Gazebo 파이프라인은 raycasting ON이므로). 프레임당 매핑시간은 런 간 일관(±0.06ms) → 연산 지표로 이걸 사용. fsm CPU%는 9%↓로 겸손하게만.
3. **🔥 예상 뒤집힘 — 안전이 "중립"이 아니라 "개선"**: full이 충돌 더 많음(1.53 vs 0.95/0.93, 38%↓) + clearance도 나쁨(0.33 vs 0.43). 메커니즘 = **full-view가 ROG-Map을 과밀 점유시켜 dense 필드에서 SUPER 계획을 열화**(2026-07-02에 seed7에서 관찰했던 효과가 11 seed × n=55에서 재확인). → 논문에서 "저감해도 안전 유지"가 아니라 **"저감이 오히려 계획 품질·안전을 개선"**으로 쓸 수 있음(단, 이 충돌 수치는 SO3 컨트롤러 트래킹 오차가 섞인 상대 비교임을 명시).
4. **adaptive의 자리 확보 — 완주율 최고 95% (52/55)**: full 82%, sector 85%, adaptive 95%. 충돌도 최저(0.93). 데이터 저감은 sector와 동일(64.5%). → **"velocity-정렬 adaptive = 저감 유지 + 최고 완주율"** — 주인공은 아니어도 정당한 기여로 논문에 들어감.
5. per-seed 노이즈 존재(seed5 sector 충돌 4.0, seed3 adaptive 2.0 등) — 개별 seed 수치는 흔들리나 전체 순서(full 최다 충돌, sector/adaptive 저감+안전)는 유지.

### 논문 숫자 (JKICS 초안용 확정)
- 전송 데이터 **64.6% 저감** (8414→2974 pts/frame, 11맵×55런)

## 2026-07-28 (계속) — 예상 반박 선점: "링크를 30Mbps로 넉넉히 잡으면 되지 않나?"

### 질문
사용자: "무선링크를 30mb를 쓰면 해결되는거 아니야?" — full(27.15Mbps)이 30Mbps 링크에선
전송시간 90.4ms(<100ms 예산)로 기술적으로 버틴다는 정확한 지적.

### 답변 (인정 + 4가지 이유로 반박)
**"맞다, 기술적으론 된다"를 먼저 인정.** 단 그 전제("30Mbps급을 항상 확보 가능")가 일반적이지
않은 이유 4가지:
1. **여유 마진 부족**: 90.4/100ms=가동률90% — 실제 링크는 거리·NLOS·간섭으로 흔들려서 짧은
   저하만으로도 예산초과. sector(가동률32%)는 여유 큼.
2. **거리-대역폭 트레이드오프**: 동일 하드웨어도 거리 늘면 SNR↓→대역폭↓(RF 물리법칙) — 근거리
   30Mbps 링크도 SAR·점검 같은 원거리 운용에선 수Mbps대로 떨어짐.
3. **하드웨어 비용·중량·전력**: 30Mbps급 라디오가 6.5Mbps급보다 무겁고 비싸고 전력 소모 큼.
4. **스웜 공유채널**: 동일 30Mbps 채널에서 full은 기체 1대, sector/adaptive는 4대+ 동시 운용.

**정직한 결론**: "sector 없이는 절대 불가능"이 아니라 "sector는 더 넓은 범위의 링크품질·거리·
기체규모·다중기체 상황에서 안정적으로 동작하고, 확보 가능한 링크에서도 훨씬 큰 여유를 준다."
— 과장 안 하고 정확한 강도로 주장.

### 조치
- `paper_story.md` §4.3.1 신설(예상 반박 선점), 커밋.

반경이 커지면 같은 1 m 표면 간격이어도 명목 미션선을 막는 장애물과 회피 분기가 늘어난다.
선행 100 Hz odom 정밀분석에서 접촉은 약 3 m/s에서 발생했고, 몸체 여유 1 m에서 접촉까지
0.34~0.38 s밖에 없었다. adaptive 충돌 대상도 속도 콘 안에 있어 필터 누락으로만 설명되지
않았다. 미관측 공간을 free로 계획하는 설정, 가림, 실효 맵 갱신률, 0.1 s 선행 궤적 커밋이
겹친 것이 가장 타당한 공통 메커니즘이다.

원시 `collisions` 합계는 물리 충돌 횟수로 쓰지 않았다. 현 모니터는 원통 안쪽에서 최신 표면점
거리가 다시 0.20 m보다 커지면 하나의 관통을 여러 번 셀 수 있다. 따라서 이번 표에서는 중복에
강건한 “접촉이 한 번이라도 표시된 런 수”를 사용했다.

### 결론과 다음 작업

adaptive는 데이터 저감이 가장 크고 접촉 런 비율이 가장 낮았지만, sector와의 14% 대 16%
차이는 작다. v5의 “0충돌·안전성 무손실” 결론은 v6에 적용하지 않고 폐기했다. 다음에는
실제 고체 원통 signed distance로 충돌을 판정하고, cloud/occupancy/A* path/position command를 함께
기록해 “못 봤는지”와 “봤지만 못 피했는지”를 분리해야 한다.

## 2026-08-04 — full이 sector/adaptive보다 접촉 런이 많은 이유 재분석

### 질문과 분석 방법

5회 캠페인의 seed1~10에서 full 15/50, sector 8/50, adaptive 7/50 접촉 런이 나왔다.
“360°를 모두 보는 full이 왜 더 나쁘나”를 확인하기 위해 각 런의 ROG performance 로그 행 증가량을
미션시간으로 나누어 실효 맵 갱신률을 계산했고, seed·모드별 점수와 대조했다.

### 결과

- seed1~10 평균: full **3.88 Hz**, sector **4.87 Hz**, adaptive **4.89 Hz**.
- seed10: full **1.56 Hz**, sector **2.64 Hz**, adaptive **3.09 Hz**.
- seed10 평균 점/frame: full 35,913, sector 10,888, adaptive 10,537.
- 3 m/s 이동에서 seed10 한 갱신 사이 이동거리: full 약 **1.92 m**, sector 1.14 m,
  adaptive 0.97 m.
- seed4~6의 접촉 런은 full 4건, sector/adaptive 0건이었고, 큰 장애물 seed9~10에서는
  full 8/10, sector/adaptive 각각 6/10으로 격차가 줄었다.

### 해석

full은 공간 정보량은 많지만 한 메시지가 커서 ROG가 처리하는 시간 프레임 수가 줄어든다.
QoS가 최신 프레임 위주이므로 밀린 프레임은 누적되지 않고 교체될 수 있다. 반면 sector/adaptive는
후방·측면을 버리지만 충돌 위험 장애물이 있던 진행방향 ±60°는 유지하면서 맵을 더 자주
갱신했다. 미관측을 free로 계획하고 0.1 s 앞의 기존 궤적에 새 궤적을 연결하는 현 설정에서는
공간 커버리지보다 시간 신선도가 더 유리하게 작용할 수 있다.

단, 실행은 모드별로 독립이고 플래너 경로와 타이밍이 매번 달라진다. 따라서 15 대 7을
“sector가 본질적으로 full보다 안전하다”는 일반 법칙으로 주장하지 않고, 현 시스템에서
관찰된 **처리량–시간 신선도 trade-off**로 기록한다.

## 2026-08-04 — 원 논문 조건 확인 및 seed11 raw-direct 입력 경로 대조실험

### 무엇을 왜 확인했나

기존 `full`을 SUPER 원 논문과 직접 비교해도 되는지 확인했다. 논문 본문과 공개 설정을 다시
대조한 결과, 원 논문의 1080회 평가는 `random_map_2_26609.pcd` 한 장을 반복한 것이 아니었다.
110×20 m forest-like 환경에서 장애물 밀도 6단계마다 무작위 지도 10개를 만들고, 각 지도에서
최고속도 1~18 m/s를 한 번씩 적용한 60×18회이며 최대가속도는 20 m/s²였다. 현재 seed11은 공개
저장소의 dense MARSIM 예제 PCD이므로, 앞 연구일지에서 이를 “원 논문과 같은 PCD”라고 적은
표현은 부정확하다. 기존 기록은 append-only 원칙에 따라 고치지 않고 이 절에서 정정한다.

또한 현재 프로젝트의 `full`은 `/cloud_registered`를 SUPER에 바로 넣지 않는다. Python 필터가
모든 점을 복사해 `/cloud_sector`로 재발행한 뒤 SUPER가 받는다. 따라서 `full`을 원 논문형 raw
baseline으로 취급하면 필터 자체의 복사·직렬화·QoS 비용이 비교군에 포함된다.

### 구현과 실험 방법

캠페인 러너에 seed11 전용 `raw`와 `upstream` 모드를 추가했다. 두 모드는 Python 필터를 띄우지
않고 SUPER가 `/cloud_registered`를 직접 구독한다. `raw`는 현 프로젝트와 같은 최고속도
3 m/s 설정이고, `upstream`은 공개 예제 설정에 가까운 8 m/s control이다. launch에서 SUPER
config를 선택할 수 있게 했으며, 회차별 모드 순서를 순환하는 `--rotate-modes`로 실행 순서 편향을
줄였다. 먼저 각 raw control을 1회 smoke test한 뒤 다음 두 실험을 수행했다.

- 현 설정 공정 대조: seed11×`raw/relay-full/sector/adaptive`×10회, 총 40회.
- 공개 upstream 예제형 control: seed11×`upstream raw-direct`×10회.

### 현 설정 4조건×10회 결과

| 지표 | raw-direct | relay-full | sector | adaptive |
|---|---:|---:|---:|---:|
| 완주 | 10/10 | 9/10 | 10/10 | 10/10 |
| 접촉 표시 런 | 1/10 | 5/10 | 2/10 | 0/10 |
| 평균 점/frame | 66,383 | 66,476 | 21,473 | 21,828 |
| ROG mapping ms/frame | 13.405 | 14.241 | 6.182 | 6.330 |
| 실효 ROG 갱신률 | 3.26 Hz | 2.60 Hz | 4.00 Hz | 3.68 Hz |
| fsm CPU | 88.8% | 90.7% | 86.8% | 86.9% |
| Python 필터 CPU | 없음 | 10.3% | 11.8% | 11.7% |

raw-direct와 relay-full은 같은 속도·지도·SUPER 설정이고 입력 점수도 사실상 같다. Python
relay가 추가되자 mapping은 프레임당 6.2% 느려지고 실효 갱신률은 3.26→2.60 Hz, 즉 20.4%
낮아졌다. 접촉 표시 런도 1/10→5/10으로 늘어 기존 full이 입력 경로 오버헤드 때문에 불리했다는
방향성과 일치한다. 다만 모드별 n=10이고 독립 실행마다 경로가 달라지므로 이것만으로 접촉 차이의
통계적 인과를 확정하지 않는다.

adaptive는 relay-full 대비 점을 67.2%, mapping 시간을 55.6% 줄였고 10/10 완주·0/10 접촉을
기록했다. sector는 10/10 완주·2/10 접촉이었다. raw-direct도 1회 접촉했으므로 relay를 제거하면
항상 무충돌이라고 말할 수는 없다.

### 공개 upstream 예제형 control 결과와 해석 경계

8 m/s raw-direct control은 7/10 완주, 10/10 접촉 표시 런, 평균 최고속도 7.96 m/s,
완주 런 평균 39.38 s였다. 이 결과는 현재 ROS2 포트·공개 예제 PCD·최대가속도 15 m/s² 조합의
control이다. 논문의 60개 생성 지도·1~18 m/s·최대가속도 20 m/s²·당시 구현을 그대로 재현하지
않았으므로 논문의 1080회 0충돌을 반박하거나 재현한 결과로 쓰지 않는다.

### 결론과 다음 작업

원 논문과 비교할 baseline은 기존 relay-full이 아니라 raw-direct여야 한다. 이번 seed11 결과에서
adaptive는 raw-direct와 비교해도 데이터와 mapping 비용을 크게 줄이면서 가장 깨끗한 결과를
보였다. 그러나 메인 seed1~10의 full 50회는 여전히 relay-full 결과이므로, 논문 수치에서
“원본 SUPER 대비”를 주장하려면 seed1~10도 raw-direct로 다시 실행해야 한다. 더 엄밀한 원 논문
재현은 논문의 60개 지도 생성 조건 또는 자산과 18개 속도 조건을 확보한 뒤 별도 캠페인으로 한다.

## 2026-08-05 — seed11 raw-direct/adaptive 각 30회 교차 실행과 접촉 포렌식

### 왜 다시 실행했나

선행 seed11 입력경로 실험은 raw-direct 1/10, adaptive 0/10 접촉 표시 런이었다. 이 10회 결과만
보고 adaptive를 “충돌 0”으로 쓰면 한 번의 실행 변동을 안전성으로 오해할 위험이 컸다. 따라서
두 모드만 회차별 선행 순서를 번갈아 각 30회 실행하고, 접촉 순간의 센싱·맵·계획 상태를 함께
남겨 raw 접촉과 adaptive 무접촉이 실제로 반복되는지 검증했다.

### 구현과 계측 검증

`native_loop_monitor.py`에 seed11 ASCII PCD grid index를 추가했다. 정적 PCD의 occupied sample을
드론 반경 0.20 m로 팽창한 union에 중심이 들어가면 PCD 보조 접촉으로 기록한다. 100 Hz odometry의
위치·속도와 최신 raw `/cloud_registered` 거리 판정은 그대로 유지했다. 접촉 false→true 전이마다
다음을 하나의 JSON event로 저장한다.

- 위치·속도·속력·최근접점
- 1 m local raw cloud와 1 m local static PCD
- 5 m local `/rog_map/occ`, 전체 occupied point 수와 누적 수신 메시지 수
- `/visualization/frontend_path` A* 경로와 `/visualization/committed_traj`
- `/planning/pos_cmd` 위치·속도·가속도·yaw 명령

처음 실행해 보니 seed11 설정의 ROG visualization이 꺼져 `/rog_map/occ` publisher가 없었다.
빈 배열을 점유맵 기록으로 오인하지 않기 위해 실행을 중단하고, raw/adaptive reference config 모두
map sliding은 false로 유지한 채 visualization만 2 Hz로 켰다. 이후 smoke에서 publisher 1개와
subscriber 1개를 확인했고, 65개 메시지·최신 105,643 occupied point를 수신했다. 접촉 event에는
local 점유 voxel 173점, A* 144점, committed trajectory 148점과 position command가 함께 저장됨을
검증했다. 점군 전체를 100 Hz마다 다시 훑는 초기 monitor는 코어 하나의 63~70%를 사용했기 때문에,
10 Hz cloud callback에서 기체 주변 2 m를 먼저 crop해 최종 monitor CPU를 약 55~57%로 낮췄다.

계측을 완성하기 전의 smoke와 60회 예비 실행도 삭제하지 않았다.
`native_seed11_raw_adaptive_n30_pre_occupancy_capture.csv`와 해당 JSON 60개는 점유맵 발행 전
예비 결과(raw live 접촉 6/30, adaptive 3/30)이며, `native_seed11_raw_adaptive_n30_smoke*.csv`와
각 forensics 디렉터리는 PCD 판정·CPU 최적화·점유맵 publisher/counter를 단계별 검증한 기록이다.
이 예비 결과는 최종 안전성 헤드라인에 섞지 않는다.

### 최종 60회 결과

점유맵 발행과 최종 monitor를 두 모드에 동일 적용해 83.4분 동안 60/60 유효 행을 수집했다.
회차별 실행 순서는 raw-first/adaptive-first가 각각 15쌍이다.

정확히 15번씩 먼저 실행돼 순서 수는 균형이지만, adaptive-first block에 접촉이 집중된 것은
cold start·scheduler·planner 초기 분기와의 상호작용이 크다는 신호다. 그러므로 총합 8 대 14를
adaptive의 보편적 인과효과로 단정하지 않는다.

### 판정과 계측의 한계

총 89개 contact event의 필드 존재를 검증했다. 시작 0.2~1.4초 안에 발생한 5개 event는 첫 2 Hz
점유맵 발행 전에 생겨 전체 occupied point 수 0의 빈 map 상태가 기록됐고, 나머지 84개에는 local
occupied voxel이 들어 있다. PCD-only와 live-only 런이 모두 있었다. 정적 PCD sample과 MARSIM이
순간 생성한 renderer cloud의 표면 위치가 일치하지 않으므로, PCD sample 팽창은 live 판정을
보완하지만 물리 ground truth를 대신하지 못한다.

또한 최종 배치는 포렌식을 위해 ROG occupied-map 시각화를 2 Hz로 켰고 monitor도 코어 하나의
약 55~57%를 사용했다. 발행-off 예비 60회에서는 raw 6/30, adaptive 3/30이었던 접촉 방향이
최종 발행-on 배치에서 8/30, 14/30으로 바뀌었다. 이는 플래너 실행이 실시간 scheduling과 작은
타이밍 차이에 매우 민감하다는 추가 근거다. 두 최종 모드는 동일 계측이므로 그 안의 비교는
가능하지만, 절대 CPU·갱신률과 접촉률을 선행 발행-off 배치와 직접 합치지 않는다.

### 다음 작업

점유맵 시각화 publish 없이 내부 ROG 상태를 저오버헤드로 저장하는 recorder를 추가하고, 정적 PCD
sample union보다 명확한 signed mesh 또는 voxel-volume 충돌 판정을 구현한다. 같은 계측을 여러
독립 배치에서 반복해 실행시점 민감도를 블록 요인으로 분석하기 전에는 safety equivalence나
non-inferiority를 주장하지 않는다. 논문은 당분간 효율 개선과 안전성 미입증을 분리해 보고한다.

### 진짜 원인: `create_cloud()`의 `is_dense=False` 하드코딩

메시지를 그대로 재전송해(passthrough) 원래의 정상 `is_dense`를 유지해 영향이 없었다.

## 2026-08-12 — full의 잔여 접촉 원인 심층 분석: 공간이 아니라 corridor 중심정렬 문제

### 발단: "접촉 0%로 만들어야 한다"

사용자가 seed1~10 full 모드의 좌표별 접촉 지점을 기록해달라고 해서 방금 나온 150회 캠페인
JSON에서 86건을 뽑아 `results/native_seed1_10_full_n5_contact_coordinates.csv`로 정리했다.
seed별 접촉 수는 1~4는 0건, 5는 6건, 6은 4건, 7은 15건, 8은 5건, 9·10은 각 28건으로 반경이
커질수록 급증했다. 좌표를 실제 장애물 매니페스트(`seed{N}_static.csv`)와 대조하니, 92%(79/86)가
두 번째로 가까운 장애물까지 1 m 이상(중앙값 1.63 m) 떨어져 있었다 — 물리적 공간은 남아있었다.

드론 지름(0.4 m = robot_r×2)과 지도의 장애물 간 최소 표면간격(1.0 m, 실측 중앙값
1.24~1.73 m)도 확인했다. 최악의 경우에도 0.6 m는 여유가 있다는 뜻이라, "부딪히는 이유가
공간 부족이 아니다"라는 결론을 재확인했다.

### "0%가 안 된다"는 이유를 여러 각도로 반박/검증

사용자가 "SUPER는 어차피 고속을 기준으로 만든 것 아니냐"고 짚어서, 논문 본문을 다시 인용해
1~18 m/s **전체**에서 0% 충돌이 주장된 것을 확인했다(§3.5 changelog에 이미 인용). 그래서
"저속이 논문에 더 가깝다"는 근사가 성립하지 않음을 정정했다. 또 "직선으로 테스트하면 되지
않냐"는 제안에는 "직선에서는 sector/adaptive가 항상 진행방향만 보게 되니 필터 비교 자체가
무의미해진다"고 답했고, 사용자도 동의했다.

동역학(회전반경) 관점에서 R_min(v)=max(v/max_omg, v²/max_acc) 공식으로 속도별 필요
회전반경을 계산해 표로 만들었다(1 m/s→0.4 m ... 18 m/s→16.2 m). "왜 회전반경이 필요하냐,
드론이니까 제자리에서 돌고 직진하면 되지 않냐"는 날카로운 질문에는 — 물리적으로는 맞지만
(정지 후 재출발은 R=0으로 가능), SUPER의 궤적 최적화가 시간 비용을 최소화하려다 보니 "감속
후 재출발"이라는 질적으로 다른 해를 실질적으로 탐색하지 않는다고 설명했다.

### switch_dist 실험: SUPER 코드는 안 건드리고 저위험으로 검증

코드를 보니 `goal_vel_en=false`일 때 각 replan 구간의 종단속도가 기본 0으로 초기화되고,
실제 목표(`gi_.goal_p`)에 `resolution*2=0.1 m` 이내로 근접하면 명시적으로 0으로 스냅되는
로직이 있었다. 그런데 `switch_dist=1.5 m`라 이 근접 조건이 실제로는 거의 발동하지
않았을 거라 가설을 세우고, `loop24_close.txt`(switch_dist=0.3)와 `loop24_veryclose.txt`
(switch_dist=0.1, 이론적 임계값과 정확히 일치)를 만들어 v=10 m/s에서 각각 50런씩 테스트했다.
결과는 82%→76%, 82%→78%로 개선 폭이 미미했다 — 가설은 기각.

### v=10 m/s에서 5가지 config를 체계적으로 실측

다른 원인을 다시 브레인스토밍해서 `robot_r`(0.2→0.28), `max_omg`+`max_acc_thr`(2.5/17→4.0/23),
`planning_horizon`(7→14), `obs_skip_num`(2→1)을 v=10 m/s·`full`·seed1~10×5회 기준으로
각각(그리고 `robot_r`+`max_omg`+`max_acc_thr` 조합도) 실측했다
(`results/native_seed1_10_v10_margin_dynamics_ablation.csv`, 350행).

| 변경 | 접촉(기준 82%) | 완주(기준 96%) |
|---|---|---|
| `max_omg`+`max_acc_thr` | 74% | 94% (거의 무손실) |
| **`obs_skip_num=1`** | **70%** | **96% (무손실, 최선)** |
| `robot_r=0.28` | 56% | 76% (완주율 희생) |
| 셋 조합 | 50% | 76% |
| `planning_horizon=14` | (58%, 참고용) | **8% (재앙적 붕괴)** |

`robot_r`을 키우면 CIRI가 "이 거리는 위험하다"고 판정하는 기준이 엄격해져 일부 맵에서 아예
경로를 못 찾고 멈춘다(`ciri.cpp`의 `if(dis < robot_r_) return FAILED`). `planning_horizon`은
늘리면 매 replan마다 훨씬 더 긴 corridor를 이어붙여야 하는데 `replan_forward_dt=0.1`은 그대로라
시간초과가 폭증했다 — 완주율이 96%에서 8%로 무너졌다. 부작용 없이 개선된 건
`max_omg`/`max_acc_thr`와 `obs_skip_num`뿐이었다.

### 순간 회전반경을 직접 계산해서 "회전반경 부족" 가설을 재검증

앞의 R_min(v) 표가 실측과 얼추 맞아 "회전반경 부족"이 주원인처럼 보였지만, 이건 뒤집어서
계산한 근사였다(정확히는 "그 속도에서 드론이 낼 수 있는 최소 반경"이지 "지도가 요구하는
반경"이 아니었다). 사용자가 이 부정확함을 정확히 지적해서, `position_command`의 속도·가속도로
접촉 순간의 **실제** 순간 곡률반경을 R=|v|³/|v×a| 공식으로 직접 계산했다(v=10 캠페인 접촉
282건, `results/native_seed1_10_full_v10_contact_curvature.csv`). 결과: 최소 0.158 m,
10th 백분위수 3.86 m, 25th 백분위수 5.89 m, **중앙값 11.26 m**. 즉 접촉의 절반 이상은 급선회
중이 아니라 완만한 경로에서 일어났다 — "회전반경 부족"은 하위 10~25%만 설명한다.

### 근본 원인 재정립: corridor 중심정렬 미보장

이 발견을 `obs_skip_num=1`의 효과(회전 능력과 무관하게 작동)와 합쳐서 보면 그림이 맞아떨어진다.
CIRI(`corridor_generator.cpp`/`ciri.cpp`)는 A* guide path 하나를 정하면 그 선을 중심으로
corridor를 부풀리는 방식이지, 장애물로부터 최대 여유를 갖도록 능동적으로 "중앙 정렬"하는
알고리즘이 아니다. guide path 자체가 치우쳐 있으면 corridor도, 그 안에서 최적화된 실제 궤적도
치우친 채로 나온다. `obs_skip_num=1`이 장애물 포인트를 누락 없이 보게 해서 corridor를 실제
여유 공간에 더 정확히 맞춘 게 개선의 정체였다. 이 구조적 특성은 SUPER 원 코드에 원래 있던
것이고, 논문은 항상 한 방향 편도 미션만 평가해서 이게 드러난 적이 없다고 추정한다.

### 결론: 접촉 0%는 이 조건에서 config로는 도달 불가능

최악 곡률(R=0.158 m)까지 v=10에서 커버하려면 max_omg≈63 rad/s, max_acc≈633 m/s²(중력의
60배 이상)가 필요해 비현실적이다. 설령 동역학 한계를 무한대로 풀어도 corridor 중심정렬
문제(회전과 무관한 절반 이상의 접촉)는 그대로 남는다. corridor 생성 알고리즘에 "guide path
능동 중앙정렬" 단계를 추가하는 건 SUPER 알고리즘 자체를 고치는 일이라, sector 필터라는 본
논문 범위를 벗어난다고 보고 시도하지 않기로 했다.

## 2026-08-13 — v=10 접촉 조사 독립 코드 감사 정정 및 방향 전환

앞 절의 결론을 코드와 원시 JSON으로 독립 재검증한 결과, 핵심 근거였던
`obs_skip_num`이 실제로는 `box_search_skip_num_`에 저장만 되고 어디에서도 사용되지 않는
no-op임을 확인했다. baseline과 skip1 config의 유일한 차이는 이 값이므로, 82%→70%를
다운샘플링 제거 효과로 해석한 것은 잘못이었다. 같은 seed/run 번호 기준 discordant pair는
baseline→skip1에서 개선 9·악화 3(exact McNemar `p=0.146`), skip1→clearance+skip1에서
개선 4·악화 6(`p=0.754`)으로 유의하지 않았다.

추가 감사에서 다음도 확인했다.

- CIRI의 새 `distancePointToSegment()`는 point seed에서 0으로 나누어 NaN을 만들 수 있다.
- preferred plane 뒤의 장애물점 제거 기준은 `local_margin`이 아니라 `robot_r_`이므로
  `local_margin=0.4` 로그가 최종 polytope의 균일 0.4 m margin을 증명하지 않는다.
- Exp clearance penalty의 gradient 부호는 맞지만 모든 SFC 면을 합산하고 erosion feasibility를
  검사하지 않으며 `BackupTrajOpt`에는 적용되지 않는다.
- skip1 접촉 런 35개 중 18개, clearance+skip1 접촉 런 37개 중 25개에 backup 접촉이 포함됐다.
- monitor의 `min_clearance_m`는 signed body clearance가 아니라 UAV 중심--표면점 거리이며,
  `DRONE_R`와 planner `robot_r`가 모두 0.20 m라 명시적 계획 여유가 없다.

따라서 앞 절의 "corridor 중심정렬이 근본 원인", "obs_skip_num=1이 유일한 순수 개선",
"config로 0% 도달 불가능"은 확립된 결론이 아니라 당시 가설/관측 기록으로만 보존한다.
연구 방향은 원본 SUPER 수치 복원이 아니라 반복 방향 전환에 강건한 SUPER 기반 planner를
공통 안전 계층으로 만들고, 그 동일 planner 위에서 full/sector/adaptive를 비교하는 것으로
전환한다. 첫 구현 단계는 기존 비행 동작을 바꾸지 않는 shadow trajectory validator와
Exp/Backup/stitching 구분 로그다.

### Shadow validator 1차 구현과 smoke

기존 trajectory guard를 감사한 결과, planner commit 후보는 Exp prefix와 appended Backup을
하나의 `Trajectory`로 결합하므로 전체 후보 검사는 Exp·Backup·접합 구간을 모두 포함했다.
다만 기존 `enable=true`는 즉시 거부/비상제동까지 수행했다. 이에 `shadow=true,
enable=false` 모드를 추가해 후보를 먼저 그대로 commit한 뒤 동일 validator로 관측하고,
`EXP`/`APPENDED_BACKUP`/`CARRY_BACKUP`/stitch를 구분해 로그하도록 했다. runner에는
`full_shadow_v10` 모드와 정적 PCD, stack log, 후보 통계를 배선했다.

seed2 1회 smoke는 27.52 s에 5/5 waypoint를 완주했고 live/static 접촉은 0이었다. 후보 387개
중 safe 310, unsafe 77이었지만 unsafe 중 67개는 map race(`VERSION_CHANGED` 54,
`MAP_UPDATING` 13)였고 실제 기하 판정 `OCCUPIED`는 10개(Exp 1, appended Backup 9)였다.
검증시간은 평균 23.58 ms, 최대 32.25 ms, FSM CPU는 104.2%였다. 따라서 기능 관측은
성공했지만 현재 동기식 validator는 비용과 map-version race가 커서 대규모 캠페인이나 enforce
전환에 아직 부적합하다. 다음 단계는 안정된 map snapshot/read transaction과 shadow-on/off
오버헤드 A/B다.

### Shadow 후속: map transaction, A/B, contact 상관분석, enforcement gate

ROG map 갱신에 exclusive transaction, trajectory 검사 전체에 shared transaction을 적용했다.
seed2 재실행에서 기존 map race 67건이 0건이 되어 한 검사 안에서 서로 다른 map version을
읽던 문제는 제거됐다. 0.25 s rate limit은 검사 횟수를 332→93회로 줄였고, 동일 관측 조건의
control/shadow 교차 A/B 4쌍에서 mission time 중앙 증가는 0.86 s(평균 control 26.18 s 대비
3.28%), FSM CPU 중앙 증가는 2.67%p였다. 모두 완주했고 접촉은 양쪽 모두 0이었다.

그러나 접촉이 빈번했던 seed4에서 rate-limited shadow는 접촉 3회 중 1회만 선행 unsafe와
연결됐다. 연결된 사건은 `APPENDED_BACKUP`이었고 경고 선행시간 0.353 s, 예측시점 오차
6.7 ms였다. dense 검사에서는 관측된 접촉 1회를 잡았지만 339 candidates/107.2% CPU였고,
비동기 latest-only worker로 commit 지연을 제거한 뒤에도 365 candidates/128.4% aggregate
FSM CPU가 필요했다. 비동기는 planner latency와 검사 CPU를 분리할 뿐 계산량 자체를 없애지
않는다.

따라서 `evaluate_guard_readiness.py`에 fail-closed 승격 기준을 만들었다. 현재 결과는
`keep_shadow_only`다. 통과 항목은 map race 0, rate-limited A/B 4쌍, CPU 중앙 증가 ≤5%p,
mission overhead ≤5%이고, 실패 항목은 dense contact 표본 20건 미만(현재 1건)과 dense paired
A/B 10쌍 미확보다. 이 gate를 통과하기 전에는 enforcement나 50-run 비교를 실행하지 않는다.

### 진짜 원인이던 MAP_STALE 반응 브레이킹과 관찰-불가 공간 문제

이후에도 남은 만성 실패의 실체를 추적한 결과 두 개의 서로 다른 문제가 겹쳐 있었다.

1. **`ROGMap`이 "확인된 빈 공간"과 "한 번도 못 본 공간"을 구분하지 못함.** BASE 설정의
   `raycasting.enable: false`(관측 이전부터 있던 의도적 설정)에서는 `isUnknownInflate`/
   `isKnownFree`가 하드코딩으로 항상 `false`였다. 이 상태에서 비상제동(`activateEmergencyBrake`)
   후보가 한 번도 관측되지 않은 공간을 "안전"으로 오판해 seed9에서 실제 충돌
   (`min_clearance_m=0.199`)이 재현됐다. `SnapshotGrid`에 `known_pages` 비트를 추가하고
   raycasting이 꺼진 경로에서도 히트 지점부터 역방향으로 짧게(기본 10 m) 마칭하며
   "관측됨"을 기록하도록 했고, 새 `TrajectorySafetyStatus::UNOBSERVED`를 비상제동 후보
   검사에만(`unknown_as_occupied=true`) 적용했다. `unknown_as_occupied`만 끈 대조 설정으로
   같은 시나리오를 재실행해 **동일한 충돌 시그니처가 재현**됨을 확인함으로써 상관관계가
   아니라 인과관계로 검증했다.
2. **SUPER 논문의 실제 backup-trajectory 메커니즘을 따라가려던 3연속 실패.** 논문
   (`misc/scirobotics.ado6187.pdf`)은 CIRI의 "Theorem 1"으로 backup corridor가 통째로
   known-free임을 기하학적으로 보장하며, 이를 위해 최근 1~2 s의 raw scan을 누적해 CIRI에
   직접 입력한다. 이를 그대로 구현하려 했으나 (a) map 기반 CIRI corridor로 대체한 첫
   시도는 사용자 지적대로 논문과 다른 지름길이었고 seed9에서 실제 충돌을 냈다(같은 stale
   map을 읽었으므로), (b) raw scan 누적 + "빈 포인트=실패" 버전은 LiDAR가 표면에만 반사되어
   열린 허공도 포인트가 없다는 사실을 놓쳐 생존율이 17/50으로 붕괴했고, (c) "빈 포인트=열린
   박스"로 바꾼 버전은 12/50으로 더 나빴고 새 raw-cloud 구독이 미션 내내 메시지를 한 번도
   못 받는 원인 불명 문제까지 겹쳤다. 세 시도 모두 전량 되돌렸다. `guard_cloud_sub_`가
   0건을 유지한 원인은 아직 미확인이며, 더 격리된 진단 없이 재시도할 가치는 낮다고 판단해
   보류한다.

### 진짜 병목: EMER_STOP이 유효한 목표를 버림

위 UNOBSERVED 수정 이후에도 완주율이 충돌 0을 대가로 떨어졌다. seed9 로그를 정량화한 결과
`TRAJ_GUARD_BRAKE_REJECTED`가 98회(`MAP_STALE` 61 + `UNOBSERVED` 37) 발생했고, 매번
`fsm.cpp`의 `case EMER_STOP`이 무조건 `WAIT_GOAL`로 전이하면서 여전히 유효한
`gi_.goal_p`/`goal_yaw`를 버리고 있었다. `WAIT_GOAL`은 `mission_planner`의
`GoalPubTimerCallback`이 목표를 재발행할 때만(`publish_dt=1.0 s`) 재개되므로, replan이
가능한 `replan_rate=15 Hz`보다 최대 1 s를 매번 허비했다. 105개 1 s 샘플의 FSM 상태
히스토그램에서 `WAIT_GOAL` 60%, `FOLLOW_TRAJ` 19%로 이 병목을 확인했다. 수정은 `started_`가
`true`면(비행 시작 후) 알고 있는 목표를 재사용해 `GENERATE_TRAJ`로 직접 전이하는 것이었다
(목표에 이미 도달했다면 `GENERATE_TRAJ` 내부의 `closeToGoal(0.1)` 검사가 안전하게
`WAIT_GOAL`로 되돌린다). 이 수정 하나로 seed1~10 (n=1) 완주가 48/50, 접촉 0/10, 5/5 클린
시드 9개로 이 조사 전체에서 가장 좋은 결과가 나왔다. 정식 5-run gate는 아직 수행하지 않았다.

또한 이 과정에서 "정지 상태 회전이 시야를 넓혀줄 것"이라는 가설(`is_360lidar: true`,
`GENERAL_360` 패턴으로 매 스캔 이미 360도 커버 — 무의미했음)과 "좌표가 반복되는 것을 보고
'진짜 가려짐이라 재접근이 필요하다'"고 판단한 가설(실제로는 `status` 필드를 확인하지
않아 `CLEARANCE_MARGIN`이 1~2회 재시도로 정상 해소되는 것과 완전히 다른 실패 모드인
`TRAJ_GUARD_BRAKE_REJECTED`를 혼동한 것)을 둘 다 근거 확인 없이 제시했다가 재검증 지시를
받고 정정했다. 두 사례 모두 "좌표/직관만 보고 결론 내지 말고 로그의 status 필드와 config를
직접 확인하라"는 교훈으로 남긴다. 상세 계측·재현 절차·되돌린 시도의 전체 기록은

## 2026-08-23 — replan 로그/ROG-Map 메모리 제한과 유효한 3-mode n=1

runner에는 attempt별 artifact와 memory trace, FSM RSS/PSS/swap, host/cgroup
