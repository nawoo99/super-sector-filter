# 원기둥 배경 관측 보완 진단 (2026-09-15)

## 목적과 동결 조건

사용자는 Sector의0/20 완주가 빈 입력에 따른 MAP_STALE 정지로 지배되는
문제를 지적했고, 알고리즘·planner·센서 설정을 그대로 두고 배경 원기둥을
보완한 맵 하나부터 비교하는 방향을 승인했다. 기존 J05 및 기존 결과는
변경하지 않는다. J08은 이미55/60행까지 진행된 시점이므로 그20회 시험만
마무리하도록 두고, 부모 제어기PID1935342를 SIGSTOP해 J09 신규 실행을
막았다. 비행 중인 확인 자식PID2143724에는 신호를 보내지 않았다.
따라서 기존 status.json의 RUNNING 표시는 부모의 실제 정지 여부까지
표현하지 않는다. 실행 여부는 /proc 또는 ps와 함께 확인해야 한다.

## 사전 지정한 새 맵 K01

- 이름: `cyl2_k01`, 부모: `cyl2_j05`.
- 기존389개 원기둥의 CSV 좌표·반경·역할을 그대로 유지한다.
- x/y=±32 m 외곽 정사각형에2 m 간격, 반경0.4 m, 높이3 m 원기둥을
  추가한다.128개 후보 중 기존 장애물과 표면 간격0.2 m를 지키지 못하는
  두 위치(-32,-18),(-32,24)를 제외해126개 추가, 총515개다.
- 이는 지면/벽/가짜 센서 반환이 아니라 모든 모드에 동일하게 존재하는
  정적 원기둥이다. 추가 장애물로 전체 수와 잠재 관측점 수도 변하므로
  이전 J05와 연산량 차이를 알고리즘 개선으로 해석하지 않는다.
- 기존 feasible centerline의 세 부분 최소 body 여유는 각각 약0.40 m로
  유지된다. 원기둥 center가15 m와±45° 안에 드는 XY proxy는 모서리별
  5° 간격 yaw 표본에서 최소5개 이상이다. **이는 차폐·센서 스캔 패턴을
  반영한 관측 보장이 아니다.** 실제 실행 ACK 계측으로 확인한다.
- PCD는 기존 CSV 정밀도에서 다시 생성되므로 원본PCD의 bit-identical
  점 부분집합은 아니다. 센서YAML은 pcd_name만 변경한다.

## 시험과 판정

Full/Sector/Adaptive를3회씩 총9회 실행한다. 묶음별 순서는 F/S/A,
S/A/F, A/F/S다. 모드별 성능 실패도 보존하며 나머지 진단을 수행한다.
계측 또는 infrastructure 유효성 오류는 기록 후 중단하고 자동 대체하지
않는다. 기존180초 mission 제한, v7,45° 및 ACK 재요청0/off를 유지한다.

별도의 읽기 전용 소형 observer가 /rog_map/cloud_process_ack와 odometry를
받는다. command/cloud/request를 발행하지 않고 유효 스캔 처리 ACK 시각만
기록한다. 첫 odometry 이후10초 warmup은 제외하고 이후 ACK 수, 평균빈도,
최대 무응답 간격(마지막 odometry까지의 침묵 포함)을 보고한다. 이 ACK는
ROG-Map에서 입력 유효성 검사를 통과해 실제 처리된 스캔에 대해서만 나온다.
개별 Full refresh의 exact ACK와 일반 map ACK cadence는 다른 지표다.

추가 observer가 붙었으므로 이9행은 **진단 전용**이며 기존 개발/n20 행이나
논문 CPU 비교에 합치지 않는다. 후보 파일의 이름이나 출력폴더가 결과
자격을 바꾸지 않는다. 지속적 MAP_STALE/빈 입력이 해소됐는지 먼저 보고,
그다음 실제 완주·접촉 차이를 본다. 세 모드가 전부 완주하면 배경 관측
보완에는 유용한 결과지만 Stress 성능 분리 성공으로 부르지 않는다.

기존 runtime/바이너리/계측 소스는 수정하지 않는다. 새 offline geometry
helper와 별도 진단 wrapper만 추가한다. 새 맵 자산은 SUPER runtime에서
생성 후 문서 저장소의 대응 디렉터리로 미러링한다. 첫 비행 전 helper 및
ACK 간격 집계11개 단위 테스트가 통과했다.

출력: `results/cylinder_background_diagnostic_20260915/cyl2_k01/`.
실행: `PYTHONNOUSERSITE=1 python3 scripts/native_campaign/cylinder_background_diagnostic.py cyl2_k01`.
기존 J05와 J08의 원자료를 덮어쓰거나 삭제하지 않는다.

## 17:18 KST 준비/실행 경계

새 helper/진단 wrapper와11개 테스트는 준비됐지만 K01 자산 생성 및 비행은
아직 시작하지 않았다. J08은58/60행(Full19, Sector20, Adaptive19)이며
마지막 Adaptive가 resource preflight에서 대기 중이다. 사용 가능 메모리가
약6.8--6.9 GiB로 동결 기준7168 MiB보다 낮다. 기준은 변경하지 않는다.
Pylance PID1486192의 RSS는 약2.3 GiB다. 사용자의 편집 환경이므로 종료
권한을 별도로 질문했으며 아직 종료하지 않았다.

J08 자식PID2143724가 끝난 뒤에만 일시정지된 부모를 정상 종료하고 K01을
생성하는 대기 작업을 시작했다(PTY session71133, 대기 상한600초).
이 작업은 새 비행을 시작하지 않는다. 이후 재개 시에는 J08 result.json,
부모/자식 /proc 상태, K01 manifest 존재 여부를 먼저 확인하고 중복 생성·
중복 비행을 피해야 한다. 실패/중단 표본은 그대로 보존한다.

추가 offline 확인: J05 Sector20개의 실제 최종 정지 위치에서5° 간격
모든 yaw를 훑은 XY center proxy의 최소 관측 원기둥 수는 원본에서모두0,
추가 배경을 넣은 가상 배치에서는각5--8개다. 실제 raw/filter 반환 증명은
아직 아니므로 비행과 ACK 간격 계측을 대체하지 않는다.

## 17:32 KST 재개

사용자가 필요한 프로세스 외 종료를 승인했다. Pylance PID1486192와 JSON
언어 서버PID2084263에 SIGTERM을 보냈다. VS Code가 Pylance를 자동 재시작해
후속PID2244611도 종료하고, 재색인 전 새PID2245516을 SIGSTOP했다(RSS~1 MiB).
편집 파일·VS Code 연결·Codex extension host·실험 프로세스는 유지했다.
Pylance 재개가 필요하면 해당 PID/명령을 확인한 후 SIGCONT할 수 있다.

J08은 마지막 Adaptive의 resource preflight600초 timeout으로 종료됐다.
실제 비행이 시작되지 않았고 원자료58행(Full19/19, Sector0/20,
Adaptive19/19, 모두 접촉0)만 존재한다. 미실행2회를 실패나 성공으로 세지
않으며20회 완료로 표시하지 않는다. 기존 제어기는 사용자 요청의 새 맵
진단 전환을 위해 종료됐고, 이전 제어기의 마지막 state는
STOPPED_FOR_DIAGNOSIS/Controller interrupted by signal15다.

K01은 실제 생성·미러링 완료(515개 원기둥,798250개 PCD점). 새 진단
PID2244976이 단일 비행으로 시작했다. Full run1은67.19초 완주·solid접촉0,
유효성 통과이며 warmup 뒤 ACK 최대간격0.1255초, 평균10.002 Hz다.
현재 Sector run1이 진행 중이다. 결과 기준은 새 진단 status/CSV이며,
부모의 기존 selected-map 목록이나 과거 진행 배너를 최신 상태로 읽지 않는다.

### ACK 시간 창의 사후 보완과 원자료 보존

첫 Sector 결과에서 원래 observer의 최대 ACK 간격1.305초가 확인됐다.
하지만 이는 목표 도착 뒤 simulator/observer 종료 사이의 침묵을 포함한다.
따라서 **첫 Sector 결과를 본 뒤** 추가 분석으로, 성공 비행은 solid observer의
5번째 waypoint 도착 시각에서 시간 창을 닫았다. 기존 원자료/원래 집계는
그대로 보존하고 `summary.json`에 두 집계를 나란히 기록했다. 실패 비행에는
가상의 도착 시각을 부여하지 않는다. 두 시간 창 모두 첫 odometry 뒤10초를
제외하며, 첫/마지막 ACK 바깥의 창 경계 간격도 포함한다.

| 모드 | 목표 도착까지 최대 ACK 간격(s), 3회 중 최댓값 | 종료까지 포함한 원래 최댓값(s) | 최소 solid 여유(m), 3회 중 최솟값 |

Sector의 비행 구간 ACK는 각각685/752/744개이며 모두 committed=true,

### 해석과 다음 단계

1. J05의 관측 부족/liveness 정지를 외곽 원기둥 추가만으로 재현하지 않게
   만든 탐색적 증거다. n3와 추가 observer가 있는 비교이므로 확정적 인과
   검정이나 최종 n20 검증은 아니다. J05의20회에 이3회를 합치지 않는다.
2. **K01은 Stress 성능 차이 목표를 달성하지 못했다.** Sector도 전부 완주했다.
   이 결과로 Adaptive의 충돌 예방 또는 완주 우위를 주장하지 않는다. Full의
   시간 변동도 크며, 이 소표본을 속도/연산량 우위의 증거로 사용하지 않는다.
3. K01을 배경 관측이 유지되는 대조 맵으로 보존한다. 다음 map-only 탐색은
   이 배경을 고정하고 안쪽 원기둥의 배열·반경·간격만 바꿔, 회전 중 Sector
   밖 장애물이 기존 경로와 충돌 위험을 만드는지 trajectory audit부터 본다.
   맵별 Full 우회 여유와 Sector 유효 입력을 함께 확인해야 한다.
4. 새 후보에서3모드 진단을 통과하고 실제 차이가 생겼을 때만 독립된 표준
   n20로 진행한다. 차이가 없거나 Full/Adaptive가 실패한 표본도 보존하며,
   결과 의존적 선정과 적용 환경의 한계를 논문에서 명시한다.
